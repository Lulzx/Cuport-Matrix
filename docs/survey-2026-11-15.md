## 1. Recommendation

**Build Cuport-Matrix: an independent, cross-tool, cross-hardware conformance
and divergence matrix for CUDA on Apple GPUs.**

Concretely: a corpus of small CUDA probes, each with an oracle that does not
need an NVIDIA GPU (the CUDA specification, a CPU reference, or a committed
reference vector), run unchanged through every CUDA-on-Metal tool that will
accept it (CuMetal, mvcc, MUDA, Bare CUDA Metal; MetaXuda for the Numba
subset), on three hardware lanes (self-hosted M6, GitHub-hosted paravirtual
Metal, community M1-M5 rows). The output is a public scoreboard plus a
divergence catalogue in which every cell is one of: bit-exact, within
tolerance, documented divergence, undocumented divergence, refused with
diagnostic, silently wrong, or crash/hang.

Why this angle, in order of weight:

1. **No cross-tool suite exists.** Every tool ships its own tests on its own
   hardware. CuMetal reports 467/467 ctest and 83/83 cuda-samples on M4 Pro
   `[self-reported]`; mvcc reports its own `tests/run.sh` on M5 Pro
   `[self-reported]`; nobody has run one corpus through both. I searched
   GitHub, GitLab, Codeberg, Gitee, arXiv and the web for such a scoreboard
   and found none (section 9).
2. **The leading tools have no real-GPU CI of their own.** CuMetal's
   maintainers state CI is absent by design and track evidence in
   `.claimwire` files `[source]`. mvcc's only workflow is `brew.yml`
   `[source]`. So the matrix is not duplicating something upstream already
   does.
3. **Divergences are being found ad hoc, one at a time.** mvcc 1.2.0 notes
   that roughly 10 % of fma results differ in the last place versus an A10G
   `[source]`; CuMetal issue #204 reports a wrong result `[source]`;
   MetaXuda's scalar-argument limitation is noted only in a forum post
   `[secondary]`. A matrix turns these anecdotes into rows.
4. **Hosted macOS CI exposes a feature subset, and nobody has characterised
   it against real silicon.** GitHub's macOS arm64 runners expose an "Apple
   Paravirtual device" with no simdgroup-matrix or bf16 support
   `[source: actions/runner-images #7085; mvcc tests/run.sh note]`. A matrix
   with a paravirtual lane and a real-silicon lane measures that gap
   directly.
5. **No project has M6 data.** M6 was announced 2026-08-25 and shipped from
   2026-09-22 `[official-doc: Apple newsroom]`. Every result in every tool's
   README is M1-M5. The first M6 rows are a contribution on their own.
6. **It is buildable on one M6 with no NVIDIA GPU.** The oracles are spec,
   CPU or committed vectors. Section 5 lists the few probe classes that
   genuinely need an NVIDIA reference and how to source them from volunteers.

Confidence: **medium**. The gap is well evidenced (sections 3, 4, 9); the
risk is in value capture, not existence.

Top risk: **weekly tool churn.** CuMetal shipped v0.7.0, v0.7.1 and v0.8.0
within 12 days; mvcc shipped v1.1.2, v1.2.0 and v1.3.0 within 36 hours
`[source: release pages]`. A matrix that pins versions is stable; a matrix
that chases HEAD is a treadmill. Mitigation: pin tags, re-run on release,
show the version in every cell.

## 2. Opportunity scorecard

Scale 1-5 per column. Gap = how unsolved; Value = who would use it; Feasible =
one developer, one M6, four weeks to a first result; Distinct = how hard it
is to confuse with existing work; M6-valid = how much can be validated on the
M6 alone.

| # | Direction | Gap | Value | Feasible | Distinct | M6-valid | Total |
|---|---|---|---|---|---|---|---|
| 1 | **Cross-tool conformance and divergence matrix** (recommended) | 5 | 4 | 4 | 5 | 4 | **22** |
| 2 | Warp and memory-model litmus family for Metal SIMD groups | 5 | 3 | 3 | 4 | 4 | 19 |
| 3 | Portability predictor (static "will this kernel port?" analyser) | 4 | 4 | 3 | 3 | 5 | 19 |
| 4 | Cross-tool performance benchmark on M6 | 3 | 3 | 4 | 3 | 5 | 18 |
| 5 | Hosted-CI enablement kit (paravirtual-aware test harness) | 3 | 4 | 5 | 2 | 3 | 17 |
| 6 | Education: annotated CUDA-to-Metal mapping guide | 2 | 2 | 5 | 2 | 5 | 16 |
| 7 | NVIDIA library shims (cuBLAS/cuRAND on MPS) | 3 | 4 | 1 | 2 | 4 | 14 |
| 8 | Numba / PTX JIT for Apple GPUs | 2 | 3 | 2 | 2 | 4 | 13 |
| 9 | Another narrow CUDA-to-MSL compiler with better diagnostics | 1 | 2 | 2 | 1 | 4 | 10 |

Notes on the losers:

- **Numba/PTX (8)**: the gap shrank sharply. MUDA PR #5 (merged 2026-11-04)
  adds PTX ingestion, a driver-API shim and a Numba path `[source]`, and
  MetaXuda already monkeypatches `numba.cuda` `[source: patch.py]`. Two
  competitors in six weeks, one with a proprietary licence, is a bad field to
  enter third.
- **Another compiler (9)**: CuMetal, mvcc, MUDA, Bare CUDA Metal, cuda4AS,
  CudaGFX and CrossTL all do source translation. CudaGFX already does coded
  diagnostics `[source]`. Distinctiveness is near zero.
- **Library shims (7)**: high value, but cuBLAS bit-compatibility needs an
  NVIDIA reference for every routine and the EULA question in section 5
  applies. Not feasible solo without NVIDIA hardware.
- **Litmus family (2)** is the strongest runner-up and is a natural second
  milestone inside the matrix (section 6, "after v0").
- **Predictor (3)** is attractive because dpct's analysis mode proves the
  shape `[official-doc: Intel]`, but its training/validation data *is* the
  matrix. Build the matrix first.

## 4. Gap evidence

### The user problem

A developer with a CUDA codebase and an Apple silicon Mac wants to know, before
spending a week: which tool should I try, what will it refuse, and where will
it run but give different numbers? Today the only way to find out is to try
each tool on each kernel.

### Evidence the problem is unsolved

| Evidence | Label | What it shows |
|---|---|---|
| CuMetal README: 467/467 ctest, 192/192 Phase 4, 83/83 cuda-samples on M4 Pro and M1 Pro | `[self-reported]` | Self-scored, two chips, no third-party run |
| CuMetal maintainers: no CI by design; evidence tracked in `.claimwire` | `[source]` | Upstream does not plan a hosted or self-hosted lane |
| mvcc: only workflow is `brew.yml`; `tests/run.sh --host` has a paravirtual note that kernels return zeros / cooperative_tensor is rejected on the hosted runner | `[source]` | Upstream knows hosted CI is a subset but has no real-GPU lane |
| mvcc 1.2.0 release note: ~10 % of fma results differ in last place vs A10G; `nvptx_oracle_pin.sh` | `[source]` | Divergences exist and are found by one-off NVIDIA comparisons |
| mvcc README "Differences from CUDA" list | `[source]` | Documented divergences exist, so "documented vs undocumented" is a meaningful split |
| CuMetal issues #204 (wrong result) and #175 | `[source]` | Users hit silent divergences in the wild |
| MetaXuda scalar-kernel-argument limitation reported on users.rust-lang.org, not in README | `[secondary]` | Undocumented limitations surface in forums |
| Bare CUDA Metal: bitwise A/B against an RTX 8000 for a single workload | `[self-reported]` | The right method, applied to one kernel on one tool |
| cuda4AS: nvcc oracle drops from RTX 5080 / Colab, status `REPORTED_NOT_REPRODUCED` | `[source]` | Another one-tool, one-author oracle approach |
| CrossTL `conformance.yml` nightly and `warp_cases.py` | `[source]` | A scoreboard exists for one tool (CrossTL) on M2 Max; nothing cross-tool |
| CrossTL paper (arXiv 2508.21256): 66 hazard kernels, 31 % of 2,585 LLM-generated kernels usable | `[paper]` | Hazard-kernel methodology is published; coverage of CUDA-to-Metal tools is absent |
| No results for "CUDA Metal conformance matrix", "CUDA Metal scoreboard", "cross-tool CUDA Apple" on GitHub, GitLab, Codeberg, Gitee, arXiv, HN | `[source: negative]` | Nobody has claimed this space |

### Who would use it

- **Tool maintainers** (CuMetal, mvcc, MUDA, Bare CUDA Metal): an external
  regression signal they currently lack; CuMetal explicitly lacks CI.
- **Downstream projects already depending on these tools**: generativeqc runs
  CuMetal on `macos-26` `[source]`; kubemetal #84 asks about CUDA on Apple
  nodes `[source]`; LAMMPS #4953 discusses an Apple GPU build via CuMetal
  `[source]`.
- **Developers choosing a tool**: the scoreboard answers "which one" per
  feature family.
- **Researchers** in GPU portability and memory models (GPUHarbor, MC Mutants,
  WebGlitch authors) who need a reproducible corpus on Apple hardware.

### Why existing tools do not solve it

Each tool's test suite is written against that tool's own dialect, oracles
and expectations. CuMetal's tests assume CuMetal's launch wrapper; mvcc's
assume mvcc's `nvcc` shim. A cross-tool matrix needs probes in plain CUDA
that every tool accepts unchanged, plus oracles independent of any tool.
Nobody has written that corpus.

## 5. M6-only feasibility

### What can be done entirely on the M6

| Activity | Feasible locally | Notes |
|---|---|---|
| Install all tools | Yes | CuMetal (brew/make), mvcc (brew tap), MUDA (pip), Bare CUDA Metal (make), MetaXuda (pip, prebuilt binaries) `[source: each README]` |
| Spec-oracle probes | Yes | Launch geometry, indexing, barrier semantics, atomics return values, integer intrinsics |
| CPU-oracle probes | Yes | Reductions, scans, stencils, FP operations under IEEE rounding, using the same LCG stream |
| Cross-tool differential probes | Yes | Same probe, different tools, same hardware: disagreement is a finding even without a ground truth |
| Hardware characterisation probes | Yes | Threadgroup memory limit, SIMD width, FP64 presence, Metal 4 tensor availability, Neural Accelerator visibility |
| Self-hosted GitHub runner on the M6 | Yes | Standard `actions/runner` on macOS arm64; one machine, one label |
| Hosted paravirtual lane | Yes (free tier) | `macos-26` is GA on GitHub-hosted runners `[official-doc: GitHub changelog 2026-02-26]` |

### What genuinely needs an NVIDIA GPU, and the mitigation

| Probe class | Why NVIDIA is needed | Mitigation on M6 alone |
|---|---|---|
| Fast-math intrinsics (`__sinf`, `__expf`, `__fdividef`) | CUDA documents error bounds, not bit patterns; the only "truth" is NVIDIA output | Record ulp distance from correctly-rounded libm; classify as within-tolerance per CUDA's documented bound |
| libdevice ulp behaviour | Same | Same |
| mma / tensor-core rounding | Hardware-specific accumulation order | Classify against IEEE reference with stated tolerance; mark `[reference-vector wanted]` |
| cuRAND / cuBLAS bit-exactness | Proprietary algorithms | Out of scope for v0; later via volunteer reference vectors |
| Undefined-behaviour probes (races, uninitialised shared) | "What NVIDIA does" is the de-facto expectation | Report observed behaviour only; no pass/fail |

Volunteer-generated reference vectors: a contributor with an NVIDIA GPU runs
the probe and commits the output with `nvidia-smi` and driver version. Free
Colab T4 is an optional source but is not assumed.

### Other Apple devices

M1-M5 rows come from community drops using the same runner and schema.
Nothing in v0 depends on them.

### Apple hardware facts that shape the probes

| Fact | Label | Consequence |
|---|---|---|
| No FP64 hardware on Apple GPUs; tools emulate (CuMetal VF64 fast48 / wide48 / ieee64 modes) | `[source: CuMetal]` | fp-semantics family must record the emulation mode in the cell |
| SIMD-group width 32 maps to a CUDA warp | `[official-doc: MSL]` | warp-primitives family is meaningful; partial-warp masks are the interesting edge |
| 32 KB threadgroup memory on older chips and on the paravirtual device | `[source: runner-images #7085]` | shared-memory family includes the 32 KB boundary probe |
| Metal 4 tensor ops and M6 Neural Accelerator per GPU core | `[official-doc: Apple]` | Out of v0; a characterisation probe records presence only |

### Legal note

The CUDA EULA (as reported by Tom's Hardware and wccftech `[secondary]`, and
present in the 13.4.1 EULA PDF `[official-doc, clause not re-read in full]`)
restricts translating nvcc *output* for non-NVIDIA platforms. Cuport-Matrix
compiles plain CUDA *source* with each tool's own front-end and never commits
fatbins, PTX from nvcc, or SASS. Probes that would require ingesting nvcc
output are excluded. This is a design constraint, not legal advice.

## 6. First milestone: "Matrix v0" (four weeks)

### Scope

| Item | v0 |
|---|---|
| Probes | 40, across 8 families (below) |
| Tools | CuMetal v0.8.0, mvcc v1.3.0 (pinned) |
| Hardware | `m6-12c` (self-hosted) and `paravirtual` (hosted `macos-26`) |
| Oracles | spec, CPU reference, LCG fixed-seed inputs |
| Out of scope | MUDA, Bare CUDA Metal, MetaXuda (v1); performance; litmus tests |

### Probe families (5 probes each)

1. **launch-geometry**: thread/block indexing, 3D dims, large grids, zero-size launch, dynamic shared size parameter.
2. **shared-memory-barriers**: static and dynamic shared arrays, `__syncthreads` reductions, the 32 KB boundary, `__syncthreads_count/and/or`.
3. **warp-primitives**: `__shfl_*_sync` variants, xor with width, ballot/any/all, `__match_any_sync`, partial-warp lane masks.
4. **atomics**: int and float `atomicAdd`, CAS loops, unsigned min/max, contended shared atomics, 64-bit atomics.
5. **fp-semantics**: default fma contraction, fast-math intrinsics, denormals, FP64 presence and emulation, half/bf16 conversions, rounding-mode intrinsics.
6. **streams-events**: stream ordering, event timing, async copy overlap, default-stream sync.
7. **device-services**: `printf`, `clock64`, `assert`, device `malloc/free`.
8. **limits-refusals**: unsupported intrinsic diagnostics, oversized shared requests, cooperative-groups grid sync, texture/surface references, dynamic parallelism.

### Deliverables

- `matrix/features.yaml` and `matrix/tools.yaml` (both present in the scaffolding).
- `probes/<family>/<id>/` for all 40 probes.
- A runner that writes `results/<tool>/<hardware>/<date>.json` per
  `matrix/schema.md`.
- A generated scoreboard (Markdown) and a divergence catalogue listing every
  `undocumented-divergence` and `silently-wrong` cell with its upstream issue.
- Upstream issues filed for each undocumented divergence.
- A reusable GitHub Actions job for the hosted lane.

### Success criteria

| Criterion | Target |
|---|---|
| Cells classified (not `not-run`) | at least 90 % of 40 x 2 x 2 = 160 cells |
| Undocumented divergences acknowledged upstream | at least 3 |
| Full run on M6 from one command | under 30 minutes |
| Hosted lane | Runs nightly without manual steps |
| Hosted-vs-M6 disagreement rate | Reported as a number, whatever it is |

### Test data

All inputs from the 64-bit LCG in `matrix/schema.md`, seeded by FNV-1a of the
probe id. Oracles consume the same stream. No random, no time, no files.

### Comparison targets

Each tool's own published pass counts (section 3) are the baseline the matrix
either confirms or qualifies. The CrossTL M2 Max scoreboard is the closest
methodological comparator.

### Schedule

| Week | Work |
|---|---|
| 1 | Runner skeleton, schema validation, families 1-2, both tools installed on M6, self-hosted runner registered |
| 2 | Families 3-5; first hosted-lane run; first divergences triaged |
| 3 | Families 6-8; scoreboard generator; upstream issues |
| 4 | Re-run on any new tool releases, write the divergence catalogue, publish |

### Fallback

If week 2 slips: 12 probes (families 2, 3, 5), CuMetal only, M6 only. That
still yields the first M6 rows and the first independent reproduction of a
CuMetal pass claim.

### After v0

Litmus-style memory-model probes (scorecard #2), MUDA and Bare CUDA Metal
columns, performance columns, community M1-M5 rows.

## 7. Differentiation and novelty

### One-sentence description

Cuport-Matrix is the first published scoreboard that runs one plain-CUDA probe
corpus unchanged through multiple CUDA-on-Metal tools on multiple Apple
hardware lanes and classifies every cell, separating documented from
undocumented divergence.

### Claims that are safe to make

- First **cross-tool** scoreboard for CUDA on Apple GPUs (no prior one found;
  section 9).
- First **hardware-attributed** results including Apple M6, and the first
  side-by-side of GitHub's paravirtual Metal device against real silicon for
  these tools.
- First **independent reproduction** of CuMetal's and mvcc's pass claims.
- A **documented-versus-undocumented divergence catalogue**, a distinction no
  current tool's test suite makes.

### Claims to avoid

- "Conformance" in the Khronos sense. There is no CUDA-on-Metal specification
  to conform to; the matrix measures agreement with CUDA semantics and with
  each other. Use "conformance and divergence matrix", never "certified".
- "X % CUDA compatible". Percentages of a 40-probe corpus are not
  compatibility figures.
- "Novel methodology". Differential testing, hazard kernels and litmus tests
  are all published (CrossTL, GraphicsFuzz, GPUHarbor, MC Mutants). The
  novelty is the target and the corpus, not the method.

### Closest prior art, in order

1. CrossTL conformance scoreboard: one tool, M2 Max, nightly `[source]`.
2. Bare CUDA Metal bitwise A/B harness: one tool, one kernel, RTX 8000
   reference `[self-reported]`.
3. cuda4AS nvcc oracle drops: one tool, author's own kernels `[source]`.
4. ZLUDA's NVIDIA-verified PTX tests: AMD target, not Apple `[source]`.
5. OpenCL CTS and SYCL CTS: the structural model (feature by implementation),
   different API `[official-doc]`.
6. dpct analysis mode: the "predict portability before porting" precedent
   `[official-doc]`.

## 8. Risks and falsification checks

### Checks to run before committing to v0

| Check | How | Would falsify |
|---|---|---|
| Overlap | Compile CuMetal's own test corpus with mvcc's `nvcc` shim, and mvcc's with CuMetal | If both already pass each other's suites unchanged, the "no cross-tool data" claim weakens |
| Scoreboard search | Re-run section 9 queries monthly | A new cross-tool scoreboard appearing |
| Maintainer CI | Watch CuMetal and mvcc for a real-GPU workflow | Upstream adding self-hosted lanes removes reason 2 |
| Driver compatibility | Confirm both tools run on macOS 26.x on M6 at all | If either fails to install on M6, v0 becomes single-tool |
| Uptake | File the first three upstream issues and see if they are triaged | Silence from both maintainers lowers Value from 4 to 2 |
| Hosted-lane validity | Run family 3 on paravirtual first | If every warp probe returns zeros, the hosted lane is diagnostics-only |
| Legal | Re-read CUDA EULA 13.4.1 translation clause in full | If source-level translation is also restricted, re-scope probes |

### Standing risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Tool churn (weekly releases) | High | Medium | Pin tags; version in every cell; re-run on release only |
| Single-developer tools stall (mvcc has one developer) | Medium | Medium | Matrix rows remain valid for the pinned version |
| MetaXuda licence forbids benchmarking or redistribution of results | Unknown `[unverified]` | Low | Keep MetaXuda out of v0; read its licence before v1 |
| Small audience | Medium | Medium | Downstream users (generativeqc, LAMMPS, kubemetal) are the first readers |
| Paravirtual lane too limited to be useful | Medium | Low | It still answers "what works in hosted CI", which is itself a question people ask `[source: runner-images #7085]` |
| M6-specific breakage in tools built on M4/M5 | Medium | Positive | That is a finding, not a failure |
